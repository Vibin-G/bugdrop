WanderCalm

Frame

An ambient photo display that wakes and sleeps on your schedule, pulls at random from your starred photographs, and tells you where — or when — each one was taken.

Live prototype — the clock is real, the transitions and caption logic are the proposed behavior. The imagery is procedurally generated stand-in artwork, not photographs.

The constraint that shapes everything

Google closed the door you were planning to walk through

Before any architecture, one fact has to land, because it invalidates the obvious build. On March 31, 2025 Google removed the photoslibrary.readonly scope. Enumerating a user's library — including the favorites filter that made "all my starred photos" a two-line query — now returns 403 PERMISSION_DENIED. The Library API only sees media your own app uploaded.

The replacement, the Picker API, is a fundamentally different shape: the user hand-picks in a Google-hosted dialog and your app receives only that selection. Three properties make it unusable as a screensaver's live source:

  • Selections expire after 7 days. An unattended frame would go blank every week until someone re-picked.
  • Image URLs expire after ~60 minutes and must carry an OAuth bearer token. Google explicitly says not to store them.
  • GPS is stripped by design. Location was removed from picker responses as a deliberate privacy measure — so your "show the location" requirement cannot be met this way at all.

There is a purpose-built API for exactly this product — and you can't have it yet. The Google Photos Ambient API exists for slideshows on TVs and photo frames, with OAuth for limited-input devices. Access requires acceptance into Google's partner program. Apply in week one, because approval is slow and it is the endgame; but do not put it on the critical path.

Where the data you actually need still lives

Google Takeout's per-photo JSON sidecars carry favorited: true, geoData.latitude/longitude, and photoTakenTime — the exact three fields every live API now withholds. That is not a workaround; for this product it is the only complete source.

The resolution is to tier the paths by who's using them. You do a Takeout import once and get the full starred archive with locations. Guests you share the app with get drag-and-drop upload and the Picker, which need no export and still carry EXIF GPS on direct upload. Everyone lands in the same store.

Architecture

Own the pixels

The single most important decision follows directly from the expiry problem: never stream from Google at display time. Copy bytes into your own storage at ingest, extract metadata once, and serve the screensaver entirely from your own infrastructure. The frame then keeps working if Google changes policy again — which, on this API's track record, it will.

// ingest runs once per photo; the display never touches Google
Takeout .zip  ─┐
Direct upload ─┼─> Queue ─> parse EXIF + sidecar JSON
Picker API    ─┘         ├─> favorited? taken_at? lat/lng?
                         ├─> reverse geocode ─> "Kyoto, Japan"  (cached)
                         ├─> derivatives 1080/1440/2160 AVIF ─> R2
                         └─> row ─> D1

Display ─> GET /api/deck ─> signed R2 URLs + captions  (no Google in path)

Cloudflare is the right stack here and you already have the muscle memory from BugDrop: Workers and Hono for the API, R2 for images (zero egress fees, which matters enormously when a frame pulls a photo every 30 seconds all day), D1 for metadata, Queues for the ingest pipeline so a 40 GB Takeout upload doesn't block a request, and Cron Triggers for the nightly reshuffle.

Randomness that actually feels random

ORDER BY RANDOM() degrades badly at scale and cheerfully repeats. Use a shuffled deck instead: store an integer shuffle_key per photo, reshuffle nightly via cron, and have each display page through it by cursor. Persist the cursor so a reload doesn't restart the sequence.

Then add the detail that separates this from a stock slideshow — anti-clumping. Raw shuffle will hand you five frames from the same afternoon in a row, because that's how photos cluster. Enforce a cooldown so no two consecutive photos share a day-bucket, and bias selection to spread across years. The result feels curated rather than dumped.

The display

What's on screen, and why

The clock

Seven-segment digits drawn as inline SVG polygons — no webfont to fail, crisp at any size, themeable. Unlit segments stay faintly visible at 8% opacity, the detail that makes a digital clock read as a physical object.

The date, subscripted

Set beneath the time in letterspaced monospace at roughly a fifth the size, so the hierarchy is unambiguous at a glance from across a room.

Caption fallback chain

Place name if GPS resolved, otherwise month and year. Never both, never empty — every photograph gets exactly one line.

Legibility on anything

A photograph can be white sky exactly where your clock sits. Soft corner gradient scrims plus text-shadow guarantee contrast without a visible box.

Details worth building in from the start

  • Screen Wake Lock API to stop the device sleeping mid-slideshow. Requires HTTPS and a user gesture, and must be re-acquired on visibilitychange — it silently drops when the tab backgrounds.
  • Burn-in drift. Migrate the clock a few pixels over several minutes. On an OLED tablet left running for months, a fixed clock will ghost permanently.
  • Night mode instead of off. At "off" hours, don't blank — fade the photograph out and hold a dimmed clock. It turns an idle tablet into a bedside clock, which is the feature people will actually keep it plugged in for. Try it in the prototype above.
  • Schedule by wall-clock polling, not setTimeout. Compare local time every 30 seconds. A timer set 9 hours out will not survive DST, device sleep, or browser throttling.
  • Sunrise/sunset schedules from the display's latitude, as an alternative to fixed hours — "on at dawn, off at midnight" suits a photo frame better than 07:00.
  • Ken Burns, gently. A 1.04→1.13 scale drift over the dwell and a 2.5-second crossfade. Honor prefers-reduced-motion.

Sharing

Displays, not accounts

Your sharing requirement has one significant UX trap in it: the devices best suited to being a photo frame — an old iPad, a Fire tablet, a TV browser — are the worst devices for typing an email and password. Solve it with pairing codes. The display opens the URL and shows a six-character code; you enter that code on your phone and bind the display to a photo set and schedule. The frame never sees a keyboard.

Model a display as its own object — slug, schedule, photo set, orientation — separate from the account. One person can run several: kitchen, bedside, parents' house.

The idea that makes this spread: shared walls. A display whose photo set accepts contributions from more than one person. Everyone on a trip drops their favorites into one wall, and each household runs the same frame. That is a genuine reason for a guest to create an account, and it is the natural growth loop for a travel brand — the frame is a souvenir that keeps updating.

Guard the privacy edge deliberately: a shared link exposing exact coordinates of photographs taken at someone's home is a real harm. Store precise coordinates, but never return them from the API — resolve to a place name at ingest and serve only that. Offer per-photo-set granularity: city, country, or nothing.

Brand fit

Why this belongs to WanderCalm

Your trip records carry title, start_date, end_date, route, and home_iana_tz. A photo's taken_at falling inside a trip's date range is a clean join with no extra input — and it upgrades the caption from a place to a memory:

// caption resolution, in priority order
"Amalfi Coast, Italy · Day 4 of Italy 2026"   ← trip matched by date range
"Amalfi Coast, Italy"                          ← GPS resolved, no trip
"July 2026"                                    ← neither; graceful floor

Toggle WanderCalm trip captions on the prototype to see the difference. From that join, three features come nearly free: an auto-generated trip wall published when a trip ends and shared with everyone who travelled; a "two years ago today" mode; and trip-filtered sets — a frame showing only Italy.

The tonal fit is the stronger argument. A screensaver is ambient by definition: slow, quiet, no notifications, nothing to tap. It's the most on-brand surface a company called WanderCalm could ship, and it keeps the brand present in someone's kitchen every day between trips — which is the hard problem for any travel product.

Sequencing

Build it fast, in this order

The ordering principle: the visible 80% of this product has nothing to do with Google. Build the entire display against a local folder first, so you have something real on a tablet within a day, and confront the ingest mess only once the thing is worth feeding.

Decisions to make before you start

  • Reverse geocoding provider. Nominatim is free but rate-limited and requires attribution; Mapbox is cheap and fast. Either way, geocode once at ingest and cache by coordinates rounded to ~3 decimals — never at display time.
  • Do you keep originals? Storing only derivatives is far cheaper; keeping originals makes you a backup people trust. This changes your storage bill by an order of magnitude, so decide now.
  • Takeout upload ceiling. Exports run to tens of gigabytes and arrive as multi-part zips. Multipart upload straight to R2 with a resumable client, or a small local CLI that walks the extracted folder and uploads only favorites — the CLI is dramatically less infrastructure, and it's your own archive, so a terminal command is an acceptable ask.
  • Video. Excluding it in v1 removes transcoding entirely. Recommended.

Honest risks

What could undermine this

  • Google narrows access further. The 2025 removal was abrupt and broke many apps. Owning your copies is the entire mitigation, and it's why the architecture above puts Google strictly at the edge.
  • Ambient API partner acceptance may not come. Treat it as upside, never as a dependency. Everything above works without it.
  • Takeout is a heavy first-run. It's the honest cost of the feature you asked for, and it's one-time — but it is the single biggest threat to guest adoption, which is exactly why guests get upload and Picker instead.
  • Long-running browser tabs are unreliable. Tabs get throttled, memory-killed, and reloaded. Build a heartbeat and self-reload, keep display state server-side so a reload is invisible, and test on the specific hardware you intend to leave running for a month.
  • Terms of service. Caching a user's own photos with their explicit consent is ordinary, but Google's Photos API policy has specific language on retention. Read it before launching this publicly rather than after.
